### 2.2 ONE switch table, ONE capability answer per session

**One table (D5).** Today there are two tables for the same four switches: `CONSENT_SWITCHES` (copy: labels and descriptions, in `consent-toggle-copy.ts`) and the plan's earlier `CAPABILITY_TABLE` (behavior). They merge into **one** exported `CONSENT_SWITCHES`. Each entry carries both halves:

```ts
type ConsentSwitchEntry = {
  key: "allowLiveSession" | "allowAudioRecording" | "allowWhiteboardRecording" | "allowNoteSending";
  capability: "online" | "audio" | "whiteboard" | "notes";
  label: string;
  description: { parent: string; child: string; self: string };
  /** What turning it off does, per mode. Rendered by the notice, the editors, the decline dialog and the privacy page. */
  effectWhenOff: { online?: string; inPerson?: string; always?: string };
  /** Behavior: what the pure function applies when this switch is off. Absent for the online switch (F3): its behavior is `sessionEntryState` (org W4), which reads this entry's copy fields only. */
  offEffect?: {
    always?: Partial<CapabilityFields>;    // applies in every mode (whiteboard, notes); mirrors `effectWhenOff.always`
    online?: Partial<CapabilityFields>;
    inPerson?: Partial<CapabilityFields>;
    unknown?: Partial<CapabilityFields>;   // mode not yet chosen (waiting room); `mic.acquire: "defer"` lives here
  };
};

/** SF8: every behavior field of `SessionCapabilities` (all of them except the derived `off` list). `offEffect` may set ANY of these, so no behavior lives outside the table. */
type CapabilityFields = Omit<SessionCapabilities, "off">;
```

**`CapabilityFields` covers mic, transcript and replay, not just audio, whiteboard and notes (SF8).** The first draft left the type undefined while the truth table below sets six behavior groups from three toggles, so a reader could not tell whether `mic.acquire`, `transcript.*` and `replay.*` came from the table or from bespoke code beside it. The rule is: **the pure function starts from the all-on value of every `CapabilityFields` key and applies, for each switch that is off, that entry's `offEffect` for the current mode (`online`, `inPerson` or `unknown`); nothing else writes any key.** So the audio entry's `offEffect` carries (online) `audio: tutor_only`, `transcript.learnerVoice: false`; (inPerson) `audio: none`, `mic.acquire: "no"`, `transcript: both false`, `notes.draft: false`, `replay.audio: false`; (unknown) `audio: none`, `mic.acquire: "defer"`, `transcript: both false`, `notes.draft: false`, `replay.audio: false`. The whiteboard entry carries `always: { whiteboard.persist: false, replay.board: false }`. The notes entry carries `always: { transcript: both false, notes.draft: false }`. When two switches write the same key the **more restrictive value wins** (`false` over `true`, `no` over `defer` over `yes`, `none` over `tutor_only` over `full`), a single `mergeRestrictive` used by the function and nothing else. `off` is **derived** (a switch is listed when it is off and its entry has a non-empty `offEffect` for this mode), never hand-written. ### 2.6 Snapshot meaning and refreeze at Start (B5, D6)

Problem (CORRECTION 3): snapshot frozen at create, live record re-read at Start.

**Decision (APPROVED, Andrew 2026-10-29 16:20, Q2): the snapshot means "consent in force when the tutor presses Start".** Consent changes are forward only. A change made mid-session or later applies from the next session.
- While a session is `PENDING` (nothing recorded yet), `resolveSessionCapabilities` reads the **live** record (via `resolveEffectiveConsentForStudent`), not the snapshot. A parent who flips Online on after the tutor opened the room is respected immediately, and a child who flips it off is respected immediately.
- **The refreeze is inside the same conditional update as PENDING→ACTIVE, on both code paths.** `startWhiteboardSession` has two paths today (`actions.ts` 300–337): the org-owned path inside `withOrgRowLock`, and the plain path. Both do the live-consent refusal check **outside** the conditional `updateMany` (a read, then a check, then the write), so a second Start or a second tab can interleave. New shape, one shared helper `startSessionTx(tx, …)` called from both paths:
  1. Inside one transaction: read the inputs via the resolver using `tx` (effective record, learner claim state, requested mode).
  2. **Call `sessionEntryState` (D3, SF1), not an inline live-off rule.** Refuse with its reason if `!state[requestedMode].allowed`. This one call covers both refusals the code makes today as two separate pieces: the **no-record lock** (`assertConsentRecordExists`, `actions.ts` 241–252, which becomes the `unclaimed` / `consent_missing_*` reasons of the same function, § 2.4) and the **live-off refusal** (`refuseLive`, `actions.ts` 297–298). Start no longer calls `assertConsentRecordExists`. **Amended 2026-10-30 (feat/org-qol, the production-redaction fix): the refusal is returned data, not a thrown `ConsentError`.** A production build redacts a thrown server-action error to a generic message plus a digest, so a thrown `ConsentError` (and any client parse of its message) never reaches the tutor; only a resolved value survives. `startWhiteboardSession` therefore already returns `{ ok: true; phase: "active" } | { ok: false; reason: EntryBlockReason }` (`EntryRefusal`, `session-entry.ts`) and the clients render the line with `entryRefusalMessage(reason, learnerName)` (the `ENTRY_BLOCK_COPY` tutor column plus the Parent-account hint rule). C3a extends the `ok: true` arm with `sessionMode` and `capabilities`, and **must keep returning the refusal as `{ ok: false, reason }`**: a rollback inside `startSessionTx` throws a private sentinel that the action catches and converts to that return after the transaction unwinds (never let it escape as a thrown error). Erasure suspension and `ORG_ADMISSION_DENIED` still throw today (their controls are disabled in the UI); that is the same redaction class and a follow-up, see `docs/BACKLOG.md`. Test S5's "refusal text is the `ConsentError` message" reads as: the resolved `reason` is `live_off` and the rendered line is its `ENTRY_BLOCK_COPY` text.
  2a. **Hold seam `start:tx:between_consent_read_and_update` (B3).** `await holdPoint("start:tx:between_consent_read_and_update", whiteboardSessionId)` sits here, after step 2's reads and **before** any write, so no row lock is held while it parks. A no-op unless armed (§ 6 infra). Tests S1, S5, S8 and S13 park a Start here and change the world around it (S12 is sequential and uses no seam). **Seam-bearing transaction (SF-B):** `startSessionTx` runs in a transaction on both paths. The plain path is a new `db.$transaction(…, { timeout: 10_000 })` (today's plain path has no transaction, `actions.ts` 322–336). The org path runs inside `withOrgRowLock` with the same explicit 10 s timeout passed through (§ 3.5). **The optional `timeout` on `withOrgRowLock` is added in C3a**, because this org Start path needs it. C4b is what passes `ORG_STAMP_TX_TIMEOUT_MS` (30 s) from the two org stamp callers. A parked seam is capped at 3 s (§ 6 infra), well inside it. S1, S5, S8 and S13 run on a **plain-owned tutor** so a parked Start never holds the org lock; at most one org arm exists, and it uses a **single** Start (no second Start queued behind the org lock).
  3. Run the conditional `updateMany` (`sessionPhase: "PENDING"`, `endedAt: null`).
  4. **Only if `count > 0`**, **upsert** the `SessionConsentSnapshot` row (R1): create it if missing, else update `consentRecordId`, `consentRecordVersion`, the four toggles and `frozenAt = now`. `SessionConsentSnapshot.whiteboardSessionId` is unique, so there is never a second row (`prisma upsert` on that key). **Why an upsert and not an update (restated, R1 / re-review 2):** a snapshot-less session can only be a **legacy row** (§ 1c item 20): `createWhiteboardSessionCore` refuses an unclaimed learner or one with no record before inserting (`create-session-core.ts` 149–160), so new sessions always get a row from `createSessionConsentSnapshot` (`create-session-core.ts` 215). An update-only refreeze would touch zero rows on a legacy PENDING session that is Started, the session would keep reading as legacy (`hasConsentSnapshot = false`, § 2.2), and a family's whiteboard-off choice would be ignored. The upsert is kept: **harmless on new sessions** (the row exists, it updates), and the **one writer that makes "every ACTIVE session has a row" true** for a Started legacy row. If `count === 0` (already ACTIVE or ended), **do not touch the snapshot**. This is what stops a second Start or second tab from re-freezing an ACTIVE session.
  4a. **The freeze must find a record, and the rule must still allow the mode (SF1).** `freezeConsentSnapshotTx` re-reads the effective record through `tx` and **returns `no_record` instead of writing** if there is none. Start then **re-runs the same pure `sessionEntryState` over the values it just froze**: if either the freeze found no record or the rule now disallows the requested mode (a family flipped online off, or the record was tombstoned, between step 2's read and this write), Start **throws, rolling the whole transaction back**, including the PENDING→ACTIVE update from step 3. The session stays PENDING, no snapshot row is written or changed, the tutor sees the refusal reason. Cost: one extra statement per session. **Clock rule (SF-F, re-review 3).** Today the helper's third parameter is `now` and it writes that one value into `endedAt`, `durationSeconds` (25–28), participant `leftAt` and token `revokedAt` (`stale-session-stamp.ts` 9–14, 33, 50–56). So the parameter is renamed `endedAt` and **`endedAt` and `durationSeconds` use it**. Participant **`leftAt` is set to that same `endedAt` (never later)**: for the four existing callers that instant is already real server time, and for the reaper it is the back-dated last-activity instant. The helper takes one real server `serverNow = new Date()` at entry and uses it for `boardPurgeRequestedAt`, for `freezeConsentSnapshotTx`'s `frozenAt`, and for token `revokedAt` (the moment the token is really revoked). `leftAt` does not use `serverNow`. For the four existing callers nothing changes in practice (all four pass a real `new Date()`: `org-scope.ts` 653 and 1043, `org-force-end-touch.ts` 31, `actions.ts` 1404 and 1410). Test **G19** (§ 6k). Inside the same transaction as `endedAt`:

**Why no URLs are stored, and why the purge never deletes anything it was handed (R2).** The first draft kept `boardPurgeUrls` (the client's events and snapshot URLs, plus the old `eventsBlobUrl`) "as a belt to the prefix suspender". Both jobs receive the deadline as an argument (`runStaleSessionReaper({ now, mode, deadline })`, `runBoardPurgeSweep({ now, deadline })`, the shape of `runTranscribeSweep(now)`) and check it between candidates (the pattern at `transcribe-sweep.ts` 41–45, 72, 134); **neither starts a clock of its own.** The constants live in **one config file** (the shape of `transcribe-sweep-config.ts`, which sets `TRANSCRIBE_SWEEP_TIME_BUDGET_MS = 240_000` against a 300 s ceiling, lines 19–20, leaving 60 s): `SESSION_REAPER_TIME_BUDGET_MS = 60_000` (a cap on the reaper's share), `BOARD_PURGE_SWEEP_MIN_WINDOW_MS = 170_000` (the purge's guaranteed minimum, **not** a timer; it replaces the earlier `BOARD_PURGE_SWEEP_TIME_BUDGET_MS`), `SESSION_CLEANUP_MARGIN_MS = 60_000`. **60 + 170 + 60 = 290 s ≤ 300 s.** A single candidate in flight when a deadline passes is what the margin absorbs; **UNVERIFIED:** the longest single reaper or purge candidate (a prefix list plus its deletes) fits in 60 s, which the executor measures against the harness and records.   **The sweep query selects only rows that can make progress now, so rows that cannot never occupy the batch (F6).** Today's transcription sweep is the cautionary shape: `findStaleTranscriptChunksForSweep` orders `updatedAt asc` + `take`, so rows that cannot progress sit at the head and starve newer ones (§ 2.3). The purge sweep predicate is:

  ```
  boardPurgeRequestedAt IS NOT NULL
  AND boardPurgedAt IS NULL
  AND consentSnapshot.allowWhiteboardRecording = false          -- a readable "persist is false" capability exists
  AND ( boardPurgeFirstPassAt IS NULL
        OR boardPurgeFirstPassAt <= now() - BOARD_PURGE_SECOND_PASS_DELAY_MS )   -- pass 2 delay has elapsed
  ORDER BY boardPurgeAttemptedAt ASC NULLS FIRST, boardPurgeRequestedAt ASC
  LIMIT <BOARD_PURGE_SWEEP_BATCH_LIMIT>
  ```

  - **Delay not elapsed** (pass 1 done, pass 2 not yet due): excluded by the third `AND` arm, so it costs nothing until it is due.
  - **Unreadable capability** (no snapshot row, or one that does not say whiteboard off): excluded by the join predicate, so a row whose capability cannot be read is never selected, never deleted from, and never in the batch. A *read error* is different from a missing row: it throws, the run logs `board_purge_sweep_error` and stops, and the next cron run retries (nothing is stamped). `runBoardPurge` still re-reads the snapshot itself before any delete (step 1 below); the predicate is the fairness filter, the re-read is the safety.
  - **A row that keeps failing** (a blob delete that errors every run) stays eligible, so it would head the queue forever. Predicate-only does not fix that once there are more such rows than the batch. **ADDED:** `boardPurgeAttemptedAt` (fourth nullable column, § 5) is stamped on every attempt and the order is `boardPurgeAttemptedAt ASC NULLS FIRST`, so a failing row rotates to the back and every eligible row gets a turn. Test **W25**: more not-yet-due rows, unreadable-capability rows and persistently failing rows than the batch size, plus one eligible row, and the eligible row is purged in one run.
  - **Stuck reporting is a separate cheap query**, not part of the batch: every run logs `board_purge_stuck ageMin=<n>` for any intent older than 24 h that is still unpurged, **including** rows the predicate excludes (a missing snapshot is exactly the case that must be loud).

`runBoardPurge(sessionId)`:
1. **Re-read the capability.** Read the frozen snapshot (not a cached value). If it is **unreadable** (error, row missing) or says `persist` is true: **delete nothing**, log `board_purge_skipped reason=capability_unreadable` (or `capability_persist`), and leave the intent for the next sweep. Never purge on a capability the code cannot read.
2. **Pass 1** (when `boardPurgeFirstPassAt IS NULL`): delete, **by prefix only (R2)**, in this order: every blob under `whiteboard-sessions/<studentId>/<sessionId>/` (events, snapshot, embedded assets; listed with the C0 `listBlobsByPrefix`), then every checkpoint blob under `whiteboard-checkpoints/<sessionId>/` (`listCheckpointBlobsForSession`), then `whiteboardEventBatch.deleteMany` again. **Nothing is ever deleted by a URL taken from the row, from a request, or from a column** (`eventsBlobUrl` and `snapshotBlobUrl` are never read by the purge). Stamp `boardPurgeFirstPassAt = now` **conditionally** (`updateMany where { id, boardPurgeFirstPassAt: null }`, SF2): the first writer wins and a concurrent second run cannot move the stamp later, which would silently extend the pass-2 delay. `deleteBlob` already swallows 404, so every step is idempotent.
   - **Prefix guard (named, re-review 2).** The pass-1 and pass-2 prefix is the exact string `whiteboard-sessions/<studentId>/<sessionId>/`, **trailing slash required** (so session `abc` cannot match `abcd…`), and it **never includes the concat audio**, which is `whiteboard-sessions/<adminUserId>/<studentId>/<whiteboardSessionId>-concat.webm` (`concat-audio.ts` 197; § 1c item 21), nor the assembled log or the placeholder events blob (§ 1c items 10 and 17). Those three have the shape `whiteboard-sessions/<adminUserId>/<studentId>/<file>`, not `whiteboard-sessions/<studentId>/<sessionId>/<file>`, so the session prefix cannot match them (an id is a UUID, so an admin id never equals a student id). A unit asserts the prefix builder returns the trailing-slash form and a W23 arm asserts a seeded concat blob survives both passes.
3. **Wait.** Pass 2 is eligible only when `now >= boardPurgeFirstPassAt + BOARD_PURGE_SECOND_PASS_DELAY_MS`. The delay is the longest time an in-flight write can still land after End: the upload-token lifetime (client tokens minted before End can still `PUT` after End; the student and learner paths refuse new tokens after End, the tutor path will after C4a) plus the checkpoint flush window (`SERVER_PERSIST_INTERVAL_MS` 1 s, `useWhiteboardRecorder.ts` 170) plus margin.

Two constants that must agree is the bug; one constant feeding both cannot disagree.
   - **Sizing (SF5).** The lifetime must outlast the **slowest legitimate whiteboard upload on the slowest connection a tutor or learner might use**, or a real upload fails halfway for the sake of a tidier purge. The largest whiteboard upload the route allows is a **25 MiB asset** (`POLICY["whiteboard-asset"].maxBytes = 25 * 1024 * 1024`, `route.ts` 96; events cap 10 MiB at 85, snapshot 5 MiB at 89; audio is out of scope). 25 MiB is about 210 Mbit, so it needs about 210 s at 1 Mbit/s upload and about 420 s at 0.5 Mbit/s. **Recommended starting value: 10 minutes (600 s)**, which covers that asset down to roughly 0.35 Mbit/s of sustained upload; the executor confirms it against the real size distribution of PDF-page and image assets (typical pages are far below the cap), picks the final number, and records the number and its derivation in `docs/PLATFORM-ASSUMPTIONS.md`. The cost is on the purge side: pass 2 becomes due about `10 min + flush window + margin` (about 13 minutes) after pass 1, so on a 15-minute cron the second pass lands on the second run after pass 1 (about 30 minutes after End in the worst case). The default (one hour) would put it at roughly 75 minutes. **Multipart uploads (SF-I, re-review 3).** `validUntil` bounds the **whole upload, not its start**: a multipart upload sends the client token on every part request (`uploadPart` takes `ClientTokenOptions`, `client.d.ts` 116 and 134), and the re-review reports each part request is checked against `validUntil`, so a slow upload whose later parts arrive after expiry fails midway. 4. **Pass 2:** repeat step 2's deletes (the prefix lists are re-run, so they catch blobs that landed in the window) and stamp `boardPurgedAt = now` **conditionally** (`updateMany where { id, boardPurgedAt: null }`). Only then is the intent complete.

**Two `runBoardPurge` calls at once are safe (SF2).** `after()` (right after End) and the sweep can both pick the same session. There is **no lease and no lock**: the design is idempotent deletes (`deleteBlob` swallows 404; prefix lists are re-run) plus **conditional stamps** (`boardPurgeFirstPassAt` and `boardPurgedAt` are each set only where they are null, so the first writer wins and no second run can move a stamp). ### 3.4 Guards against in-flight writes (B2)

1. **Batch upsert vs End.** `checkpoint/route.ts` checks `endedAt` and phase in `assertActiveSession` (63–110) and then, in a **separate** transaction (`db.$transaction`, ~187), upserts the batch. A batch that passed the check before End committed can upsert after End's `deleteMany`, leaving a row with `boardDocumentJson`. **Fix:** re-check inside the batch transaction under a row lock on the session (the End transaction updates that row, so the lock orders them): if `endedAt` is set and the frozen capability says `persist === false`, abort with 409 and write nothing. For `persist === true` behavior is unchanged (the late window stays). **The check is the FIRST statement of the batch transaction (SF-C, re-review 3), before the upsert** (today the transaction is the upsert at ~188 and then the cursor `UPDATE` at 215–220, `checkpoint/route.ts` 187–220; the lock the cursor `UPDATE` takes comes **after** the write, so a re-check placed there, or after the upsert, runs too late to order against End). Shape: `SELECT "endedAt" FROM "WhiteboardSession" WHERE id = ${sessionId} FOR NO KEY UPDATE` through `$queryRaw` as the first statement; if `endedAt` is set and the frozen capability says `persist === false`, throw, so the whole transaction (including any would-be upsert) rolls back, and the route returns 409. **Lock level, with the reason (a refinement of the review's "`endedAt` check or `FOR SHARE`"):** use `FOR NO KEY UPDATE`, **not** `FOR SHARE`. The cursor `UPDATE` at 215–220 already takes `FOR NO KEY UPDATE` on that row, and `FOR SHARE` followed by that `UPDATE` is a lock **upgrade**: two concurrent batch transactions for one session can each hold `FOR SHARE` and then each wait on the other's upgrade, a deadlock (Postgres aborts one, error 40P01, which `withDbRetry` does not retry because it matches connection errors only, `db.ts` 30–52). `FOR NO KEY UPDATE` first adds no new conflict class (the batch transactions already serialize on that row at the `UPDATE`; they now serialize one step earlier) and still conflicts with End's `FOR UPDATE`, so End and a batch order against each other whichever arrives first. **UNVERIFIED:** the throughput cost of holding that lock across the upsert at the 1 s batch cadence (one writer per session, so expected negligible); the executor measures it in C4b. A jest guard pins that the check is the first statement of the transaction callback.

### 3.9 Sessions that never end: the stale-session reaper (R3) — APPROVED (Andrew 2026-10-29 16:17, Q3)

**The hole.** Everything in § 3.2–3.5 hangs off End. A session whose tab closes, or whose tutor never presses End, has `endedAt = null` indefinitely and keeps its board, so "deleted when the session ends" has no deadline. Nothing ends such a session today: `vercel.json` has two crons, `/api/cron/transcribe-sweep` (every 15 min) and `/api/internal/erasure/process` (every 6 h), and neither touches `endedAt`. The only automatic ends are lazy and org-only: `touchOrgForceEndIfDue` stamps "first read after the force-end deadline. **A row nobody reads stays unended**" (`org-force-end-touch.ts` 8–10), and the org status / member-removal paths stamp the sessions they find at that moment (`org-scope.ts` 670, 1081). The student page already lists open sessions with a Resume-or-End prompt (`students/[id]/page.tsx` 45, 146–182) because they accumulate.

**Design (APPROVED, Andrew 2026-10-29 16:17).** A background job ends any session with no activity for 24 hours, through the shared stale/forced End path, for every session. The whiteboard-off purge follows.
- **Where (B1; replaces the earlier "existing cron route").** `runStaleSessionReaper({ now, mode })` runs on the **new** `/api/cron/session-cleanup` route (§ 3.3), **first**, then the purge sweep, each in its own try/catch, with a **deadline passed in from the route's start time** (SF-G, § 3.3: `reaperDeadline = min(routeStart + SESSION_REAPER_TIME_BUDGET_MS, routeDeadline)` with `SESSION_REAPER_TIME_BUDGET_MS = 60_000`; `runStaleSessionReaper({ now, mode, deadline })`, the shape of `runTranscribeSweep(now)`, so it is testable the same way). It no longer shares a route, a budget or a failure with the transcription sweep. The `vercel.json` entry and the budgets config are C4b's (which creates the route); this wave (C4c) adds the job to it.
- **Candidates.** `endedAt IS NULL` **and** last activity older than 24 h **and** the appointment condition below. `WhiteboardSession` has no `updatedAt` (checked, `schema.prisma` 375–547), so "last activity" is the greatest of the columns that already record it: `createdAt`, `activatedAt`, `lastActiveAt` (both-parties heartbeat; null when nobody is connected), the newest `WhiteboardEventBatch.createdAt` (the board writes about once a second while anyone draws; indexed `[whiteboardSessionId, createdAt]`), the newest `SessionRecording.createdAt`, and the newest `SessionParticipant.joinedAt`. No new column and no write on the hot path. Only open sessions are scanned, which is a small set at pilot scale; there is no `endedAt` index and none is added here.
- **Why 24 h.** It equals `JOIN_TOKEN_LIFETIME_MS` (`actions.ts` 385): by then every join link the tutor issued is already dead, so ending the session removes nothing a participant could still use.
- **Why the appointment condition.** A scheduled room is get-or-create by `scheduledSessionId` (unique), and `createWhiteboardSessionCore` returns the existing row **whether or not it has ended** (`create-session-core.ts` 114–121). A tutor can open a room ahead of the appointment (the bridge applies the join window to learners and AH principals only, `schedule-bridge.ts` 90–104). Reaping that session before the appointment would make the appointment's room permanently an ended session. Test G5.
- **The null-`endAt` rule (B2).** `ScheduledSession.endAt` is **nullable** (`schema.prisma` 1149; `startAt` is at 1148 and not nullable), so "the appointment's `endAt` is in the past" is undefined when it is null, and the first draft would have thrown or silently reaped. The rule, in one sentence: **activity-idle for 24 h alone decides; the appointment only ever delays, never accelerates.** Concretely, `delayUntil = scheduledSession.endAt ?? scheduledSession.startAt` for a session linked to an appointment, `delayUntil = none` otherwise; the session is **not** a candidate while `now < delayUntil`. So a null `endAt` imposes no *end* time and falls back to the appointment's `startAt` (an appointment that has not begun is not "idle"; **ADDED, veto-able**: the decision text said only that `endAt` never accelerates, and the `startAt` fallback is my reading of why G5 exists). An appointment can therefore never make a session reaped **sooner** than 24 h idle, whatever its fields say. Test **G13** covers a null `endAt` with a start in the past (reaped), a null `endAt` with a start in the future (not reaped), and a non-null `endAt` in the future (not reaped).
- **How (B2): a conditional End, never a bare stamp.** `stale-session-stamp.ts` guards only `endedAt: null` (15–25 early return, 30–37 `updateMany where {id, endedAt: null}`); it has **no idle check**, so a scan-time decision alone would end a session someone resumed a millisecond later, permanently, and purge its board if recording is off. So the reaper never calls the helper bare. Per candidate:
  1. **Scan** (outside any transaction): list a bounded batch of open candidates (`endedAt IS NULL`, `createdAt` older than 24 h as a cheap necessary pre-filter, oldest first), and for each compute `evaluateSessionIdle(db, id, now)`.
  2. **Hold seam `reaper:between_scan_and_stamp` (B3).** `holdPoint(...)` between the scan's decision and the stamp transaction. No-op unless armed.
  3. **One transaction:** `lockWhiteboardSessionRowTx(tx, id)` (`SELECT … FOR UPDATE`, § 3.2); if the row is gone or `endedAt` is set, skip (`reason=already_ended`); then **`evaluateSessionIdle(tx, id, now)` again, with fresh reads inside the lock** (the same one function the scan used: one predicate, two call sites, no second copy); if it is no longer idle, return `not_idle` and **write nothing**; only if it is still idle call the shared `stampStaleWhiteboardSessionEnd(tx, id, lastActivityAt, notesForbidden=false)`, whose own `updateMany where endedAt null` is the second guard.
  The lock is the same row lock the batch writer takes through its cursor `UPDATE` (`checkpoint/route.ts` 215–220), so a batch commit lands either before the lock (the re-check sees it, `not_idle`) or after the reaper commits (the writer then finds `endedAt` set). **Residual, accepted and recorded:** writes that do not take the session-row lock (a `SessionRecording` registration, a `SessionParticipant` join) can commit between the re-check and the reaper's commit, a window of a few statements; the consequence is the existing late-window behavior of any End. The 24 h bar makes it astronomically unlikely and the kill switch below makes the first weeks observable.
  **One End semantics: it ends every such session, not only whiteboard-off ones.** The helper already writes the PENDING snapshot (R1) and the purge intent (§ 3.2), so a whiteboard-off session gets its board purged by the sweep that follows, and a PENDING session is handled by the same rule as a PENDING End. No `after()` (there is no request); the sweep is the executor.
- **Kill switch and first-deploy dry run (B2): `CONSENT_REAPER_MODE = off | dry_run | enforce`.** Read per run through the one env module (`src/lib/env.ts`, whose pattern is a zod-validated schema, `WHITEBOARD_SYNC_URL` at line 90, plus a raw `process.env` map from 159) by one pure `resolveReaperMode(raw)`. **Unset, empty or unrecognized resolves to `dry_run`**, never `enforce`, so the safe state is also the default and the typo state (a non-empty unrecognized value also logs `[slc] action=reaper_mode_invalid raw=<value>` once per run). `off`: the job does nothing and logs `reaper_off` once per run. `dry_run`: the job scans and runs the scan-time **and** the in-transaction idle evaluation exactly as `enforce` would, but **writes nothing** (read-only evaluation: no row lock, no stamp, so `dry_run` has no effect on live sessions), and logs `[slc] wbsid=<id> action=would_reap phase=<pending|active> idleSince=<iso> idleHours=<n> persist=<bool> appt=<none|delayed|clear>` for each session it would have ended. `enforce`: stamps and logs `[slc] wbsid=<id> action=reaped … idleSince=<iso>`. **C4c merges and deploys in `dry_run`. ## 9. Adversarial review — reliability blindspots

Axes from the real bar: [`../agenticPipeline/.cursor/rules/reliability-bar.mdc`](../../../../agenticPipeline/.cursor/rules/reliability-bar.mdc) (data durability; clock + ordering; race conditions on user input; cross-platform parity; observability). The first draft used the five axes as the org plan paraphrases them, which are different (B8); this section replaces it. Privacy/access, silent failure and data integrity concerns from the first draft are kept as risks under the axis they belong to.

**Sarah-trust framing.** Sarah must be able to turn a switch off and believe it: nothing recorded that she switched off, a board she never wanted kept actually gone, and a session that never loses her work when she wants it kept. If a tutor needed a backup recorder to be sure a switched-off thing was off, this wave is not done.

Ranked by reliability impact; every `[BLOCKER]` is folded into wave acceptance in § 9f, not listed and left.

### 9a. Axis 1 — Data durability

1. **[BLOCKER] DUR-1 End commits but the purge never runs (request dies, function killed, tab closed).** Intent (`boardPurgeRequestedAt`; no URLs, R2) is written inside the End transaction and the shared stale stamp, after the PENDING snapshot write (R1); the purge sweep runs from the intent, not from a request. Acceptance: W13, W14, W22, S6, S7b. S7 is the snapshot write (C3a) and does not assert the intent.
2. **[BLOCKER] DUR-2 A client-uploaded `events.json` is not referenced by the row and survives (review B1).** The purge deletes **by session prefix only** (R2): the client-uploaded events blob is under that prefix, and the **tutor-path prefix guard (W19, prerequisite C4a)** is what makes "everything is under the prefix" true. No URL from a request or a row is ever a delete target, so a foreign or audio URL cannot be deleted (W23). Acceptance: W13, W19, W23.
3. **[BLOCKER] DUR-3 In-flight batch or asset write after End leaves board data (review B2).** Batch transaction re-checks `endedAt` under a row lock; token mint refuses after End; pass 2 removes what a pre-End token still lands; the sweep removes rows as well as blobs. **W11 asserts zero rows before any purge pass, through the hold seam, so it is red without the in-transaction re-check (R4).** Acceptance: W11, W12.
4. **[BLOCKER] DUR-4 Unreadable capability must never purge.** A purge on a misread capability would delete a board the family was promised. `runBoardPurge` re-reads the frozen snapshot and deletes nothing, retrying, if it cannot read it or it says `persist`. Acceptance: W16.
5. **[BLOCKER] DUR-5 Purge must not hit data we meant to keep.** `persist === true`, legacy sessions with no snapshot, and sessions before this wave never get an intent; audio lives under a different prefix; the assembled-events path is never prefix-deleted; **nothing is deleted by a URL the purge was handed** (W23). Acceptance: W1, W17, W9, W21, W23.
6. **[BLOCKER] DUR-6 Device-side copies: the IndexedDB stroke-log checkpoint and the `sessionStorage` scene draft (review B1, D1).** **Amended by SF3 / Q6 (PENDING ANDREW, default applied):** the checkpoint is **kept** during a whiteboard-off session (crash recovery) and **deleted** at End and on the next workspace mount when the session ended elsewhere with `persist === false`; it is never deleted on an unreadable capability (W16). The `sessionStorage` scene draft follows the same rule. Acceptance: W15, W16.
7. **[BLOCKER] DUR-7 Learner-lane chunks must not be lost or relabeled by retries (B3).** Upsert never overwrites lane identity; kick/sweep pass lane. Acceptance: A8, A9.
8. **[BLOCKER] DUR-8 Sessions that never end (R3).** A closed tab or a forgotten End leaves `endedAt = null`, so no purge intent is ever written and the board stays. **APPROVED (Andrew 2026-10-29, Q3).** The stale-session reaper (§ 3.9, C4c) ends every session idle 24 h through the shared stamp, and the purge follows for whiteboard-off ones. The decline fallback in § 3.9 is historical and does not ship. An "are you still there?" prompt is out of scope (`WB-IDLE-STILL-THERE`). Acceptance: G1–G19, W13 arm B.
  9. **[BLOCKER] DUR-9 The sweep must not starve (F6).** Rows that cannot progress (delay not elapsed, unreadable capability, persistently failing) must not occupy the batch. Acceptance: W25.
10. Crash / OOM / refresh / background / sleep, session with whiteboard **off**: live reload hydrates from server batches. **Under the Q6 default (the on-device checkpoint is kept)** the IndexedDB tail covers a network drop as it does for whiteboard-on sessions, so the loss window is the same as today's. **Under Q6's alternative (never written)**, up to the whole stretch since the last successful server save (`useWhiteboardRecorder.ts` 167–170: IndexedDB cadence 30 s, server cadence 1 s but network-dependent) can be lost on a drop, which is the unbounded window the re-review named (SF3) and why the default keeps the checkpoint. Whiteboard **on** is unchanged. Crash mid-End: the intent is in the transaction or it is not (atomic); the End retry is idempotent and overlapping Ends are safe (W18).
11. Network drop at End: unchanged for audio (outbox, Pillar 2). For the board, the purge is by prefix, so it does not matter whether the End call or its URLs arrived (W13). Pass 2 covers late PUTs (W12).
12. Refusal rows that sit `pending` forever (starvation) — covered by N6; rated BLOCKER under DUR-7's acceptance because a starved sweep silently stops transcribing other sessions.
13. Follow-up (no BLOCKER): a board blob outside the session prefix (impossible for new tutor uploads after C4a; the placeholder events blob holds no board content) is reachable only by the `blb` CLI. BACKLOG `EVENTS-URL-VALIDATE`: End still accepts any `http(s)` URL as the final events URL (§ 1c item 19); the purge no longer depends on it, but the field should be validated.
14. **Sync relay (F8, no BLOCKER).** No evidence it stores board state; the one thing the repo cannot settle is the upstream source and its debug logging (§ 3.10). Settled by the C0 read and W24; copy waits for it.
15. **[BLOCKER] DUR-10 Every session that reaches ACTIVE has a `SessionConsentSnapshot` row (Andrew 2026-10-29 16:23).** No consent record at Start: the session cannot start, online or in person, and the disabled Start shows the reason. The Start upsert writes the row when create skipped it. Legacy snapshot-less rows are left as they are and are not backfilled. Acceptance: S9a/b, S10a/b, and the upsert path S6.
16. **[BLOCKER] DUR-11 The reaper must never end a live session, and must ship inert (B2, B1).** A session that became active between the reaper's scan and its stamp must not be ended (the idle predicate is re-evaluated under the row lock, § 3.9); a null appointment `endAt` must not throw or accelerate (`delayUntil = endAt ?? startAt`); the job deploys in `CONSENT_REAPER_MODE=dry_run`, an unrecognized value falls back to `dry_run`, and flipping to `enforce` is an Andrew go after he reads `would_reap`; the reaper and the purge run in their own cron route with isolated failures and budgets below `maxDuration`, so neither can starve `transcribe-sweep`. Acceptance: G12–G16, G19, K1–K5.

### 9b. Axis 2 — Clock + ordering correctness

Single source of truth for `t`: **server time (`now()` on the server) for every consent/purge ordering decision.** Audio replay time stays the `MediaRecorder` elapsed clock (unchanged; this wave touches nothing there).

1. **[BLOCKER] CLK-1 Capability must be known before any recorder, lane, mic or checkpoint arms.** Ordering: Start's transaction commits the refreeze → returns capabilities → client adopts → client arms. A client acting on page-load capabilities after Start was requested is the bug (B5). Acceptance: S3, A2b.
2. **[BLOCKER] CLK-2 End vs a racing batch write.** The row lock in the batch transaction orders the two; without it a batch that passed the check can land after the End transaction's delete (B2). **The re-check is the batch transaction's first statement, under `FOR NO KEY UPDATE` (SF-C, re-review 3)**: a check after the upsert, or a `FOR SHARE` taken before the cursor `UPDATE`, either runs too late to order against End or upgrades a lock and can deadlock (40P01, which `withDbRetry` does not retry). Acceptance: W11, S14(c).
2a. **[BLOCKER] CLK-5 The reaper's back-dating must not leak into the purge clock (SF-F, re-review 3).** The reaper passes the last-activity instant only as `endedAt` and the `durationSeconds` basis, and sets participant `leftAt` to that same `endedAt` (never later). `leftAt` is not a purge-clock input. The purge intent and the snapshot's `frozenAt` use real server time, so `board_purge_stuck` (an intent older than 24 h) cannot fire on a freshly reaped session. Acceptance: G19.
3. **[BLOCKER] CLK-3 The second purge pass is timed from the server clock and the token lifetime.** The delay constant is derived from the **same** `BLOB_UPLOAD_TOKEN_LIFETIME_MS` that C4b passes as an explicit `validUntil` (verified: the `@vercel/blob` 2.3.3 default is one hour, `client.d.ts` 349/383, and `validUntil` has no hit in `src/`), plus the flush window and a margin; one constant feeds both, so they cannot disagree. Acceptance: W12 (including its no-backdate negative arm), plus a jest test that the delay constant is ≥ the token lifetime + flush window and that the token route passes that lifetime.
4. **[BLOCKER] CLK-4 Replay clock with an empty placeholder log plus audio.** `computeReplayTotalMs` already prefers audio length when `hasAudio`; the component path is UNVERIFIED. Acceptance: W20 (characterization: green before, regression guard).
5. Consent versions: the snapshot records `consentRecordVersion`; the refreeze logs before/after; after End only the snapshot is read (RP3/RP4), which removes a whole class of "live record changed under a finished session" ordering bugs.
6. Follow-up: `frozenAt` is overwritten by the refreeze; the create-time value is kept only in the log line. If an audit trail is later required, add a column; not needed for the locked rules.

### 9c. Axis 3 — Race conditions on user input

1. **[BLOCKER] RACE-1 Double Start / two tabs / Start double-click.** The refreeze runs only when the conditional update changed a row; a second Start is a no-op and does not refreeze; the Start/End/consent-flip interleavings are **forced** by the hold seams (arm → park → release, B3), so the tests cannot pass by the second call simply seeing the finished state. Acceptance: S1, S5, S8, S13, with S12 as the sequential characterization and S14 pinning statement order.
2. **[BLOCKER] RACE-2 Double End / End double-click, including overlapping Ends.** End is an `updateMany where endedAt null` taken under the session-row lock; only the call with `count === 1` writes the snapshot and the product event (C3a) and the intent (C4b). Acceptance: W18 (both arms) and S14(a) for the lock, the count gate and the single snapshot; W18b and S14(a2) for the intent.
3. **[BLOCKER] RACE-3 Consent flipped between page load and Start** (parent or child flips while the tutor's page is open). Acceptance: S3, E12, E13.
4. **[BLOCKER] RACE-4 Waiting-room mode toggled (online ↔ in person) while the mic acquire is in flight.** The gate is evaluated on each change; an in-flight acquire for a mode that became `no` is cancelled and its tracks stopped; `micAcquireSettled` still settles. **The gate lives inside the hook's `requestMic` / `requestMicAndCam` so the manual mic controls cannot bypass it (SF-D).** Acceptance: M5, M6, M9, M16.
5. **[BLOCKER] RACE-5 A late consent change must not alter a running session.** ACTIVE reads the snapshot only. Acceptance: S2.
6. **[BLOCKER] RACE-6 The reaper races activity and the tutor's own End (B2).** Scan, then stamp is a check-then-act. The idle predicate is re-evaluated **under the row lock**, and the stamp is conditional, so a session that became active, or that the tutor ended, between the two is skipped. Acceptance: G12 (both arms).
7. **[BLOCKER] RACE-7 The learner learns the mode and capabilities late, and the mic is deferred for it (B4).** The learner's mode and capabilities arrive on the `join-timer` poll in the same update as the phase flip; with audio off and the mode unknown, the learner's audio request waits; once online is known the audio acquire must still reach the tutor (M12), and audio-on sessions must not change (M15). The poll takes up to 3.5 s, so M11, M12 and E19 assert inside a 10 s `expect.poll` window (SF-I), and the ACTIVE poll makes one snapshot read (M17). Acceptance: M11–M15, M17, E19.
8. Rapid Start (in person) after Start (online) attempt: server refuses the second via the conditional update; client shows the one reason line, not a flip (E2, E3).
9. Two tutor tabs: capability is read server-side per request; no client-held authority (S1).
10. Browser back/forward bypassing the blocked page: the server check at `/join` does not depend on the client navigation (E6, E7).
11. Follow-up (no BLOCKER): mic permission prompts racing a tab switch are the existing `chainDeviceAcquire` territory; this wave adds no new acquisition path outside the gate.

## 10. Review disagreements

The review was right on every blocker. Where I checked a claim against code and it was incomplete or off, this is the evidence. None changes a decision.

1. **B1, "the IndexedDB checkpoint is not cleared … garbage-collected only when the same session URL is reopened."** Partly wrong. The normal End path **does** clear it: `markPersisted` (`useWhiteboardRecorder.ts` 1465–1470) is called from `WhiteboardWorkspaceClient.tsx` ~4695 right after End. Reopening the ended session's URL clears it (1360–1362), and opening any workspace for the same student clears that student's latest ended-session checkpoint (1396–1412), not only the same session. The review's conclusion still holds for the paths that matter: stale/forced End by another actor, a crashed or closed tab, and a tutor who never reopens that student's workspace leave the full board on the device. D1 first superseded this with "never written"; **re-review 2 (SF3) showed that overstated the recovery window, so the default is now "kept during the session, deleted at End and at next load" (Q6, PENDING ANDREW)**. I also found a second device copy the review did not name, the `sessionStorage` scene draft (§ 3.7).
2. **B2, "asset uploads have no `endedAt` guard (`route.ts:210-215`)."** True for the **tutor** path only. The student join-token path and the learner path both refuse an ended session at token mint (`whiteboard-scope.ts` 160–162, 201). The remaining gap is a token minted before End that is used after it, plus the tutor path, which also lacks the pathname-prefix check the other two have. § 3.4.
3. **B1, "the assembled blob … is not enumerable."** It is enumerable by prefix, but the prefix `whiteboard-sessions/<adminUserId>/<studentId>/` is shared across every session of that student, so it must never be prefix-deleted. The review's remedy (skip assembly when `persist` is false) is right and is what § 3.5 does.
4. **B4, "the learner-side bootstrap opens mic and camera with no consent check."** True, but for an **online** session the learner's mic is legitimately needed for the live conversation even when audio recording is off (only recording/transcription is off). So the learner gate is mode-based (`micAcquire`), not a blanket consent check. D7's "gate every opener, including the learner-side bootstrap" is satisfied by the shared gate returning `yes` in LIVE.
5. **SHOULD-FIX, "the notes sweep takes the oldest 10 pending rows … refused rows left pending starve newer rows."** Correct, and it is worse than the review says: the **chunk** sweep (`findStaleTranscriptChunksForSweep`, `updatedAt asc` + `take`) has the same shape, so refused chunks starve it too. Both are fixed by the terminal states (§ 2.3).
6. **Missing tests.** None of the fourteen was wrong. One is deliberately not a test: the **tampered-label limit** (B3) is documented, with a `docs/BACKLOG.md` entry, not asserted. A test that proves a limit exists would be theater, and the privacy copy does not claim more than the client and server paths guarantee.
